## Requirements
### Requirement: Human-readable default output
The CLI SHALL render concise human-oriented output by default rather than serializing service response objects. Every completed command SHALL explain what happened, the resulting state, anything requiring attention, and the recommended next command or action when one exists.

#### Scenario: Phase completes normally
- **WHEN** `swf next <change>` completes one phase and pauses
- **THEN** output names the completed phase, summarizes checks and checkpoint creation, identifies the next phase, and shows commands for one-phase or automatic continuation

#### Scenario: Approval is required
- **WHEN** a workflow command stops at a manual gate
- **THEN** output prominently states that approval is required, names the phase, summarizes review evidence and risks, and displays directly executable approve, request-changes, and reject commands

#### Scenario: Workflow completes
- **WHEN** the final phase and local-branch delivery complete
- **THEN** output summarizes completion, checkpoints, branch, dossier, and review or merge commands

### Requirement: Stable JSON mode
The `--json` mode SHALL emit only a versioned machine-readable result or error to standard output, SHALL contain semantic attention and next-action data, and SHALL not contain terminal decoration, progress animation, package-runner chatter generated by SWF, or interactive prompts.

#### Scenario: JSON workflow response
- **WHEN** a workflow command is executed with `--json`
- **THEN** stdout contains one parseable JSON document with result state, actual stopping phase, attention, and next actions

#### Scenario: JSON command fails
- **WHEN** a command fails with `--json`
- **THEN** stdout contains one parseable versioned error object with classification, recovery guidance when available, and a nonzero exit status

### Requirement: Ergonomic change-based selectors
Routine CLI commands SHALL resolve project and run context from `--cwd` or the current directory plus an OpenSpec change name. Explicit project and run IDs SHALL remain supported for automation, cross-project operation, and ambiguity resolution but SHALL NOT be required for the ordinary single-project path.

#### Scenario: Approve by change name
- **WHEN** exactly one gate for `test-swf` is awaiting approval in the current project
- **THEN** `swf approve test-swf` resolves the run, phase, and gate without requiring explicit identifiers

#### Scenario: Inspect status by change name
- **WHEN** a run is bound to a change in the current project
- **THEN** `swf status <change>` renders its operator projection without requiring project or run IDs

#### Scenario: Selector is ambiguous
- **WHEN** more than one attention item could satisfy a shorthand command
- **THEN** the CLI refuses to guess, displays the alternatives, and explains the minimum disambiguating option

### Requirement: TTY-aware live progress
For long-running workflow commands attached to a terminal, the CLI SHALL consume ordered service events and render bounded progress for phases, harness activity, checks, gates, checkpoints, and delivery. Progress SHALL tolerate reconnection without duplicating completed milestones.

#### Scenario: Agent executes
- **WHEN** an agent work unit starts, works, and settles
- **THEN** the terminal shows the phase and agent progress followed by a completion duration before rendering final command guidance

#### Scenario: Event connection is interrupted
- **WHEN** the progress stream disconnects during active work
- **THEN** the CLI reconnects from the last observed sequence and continues without losing or duplicating durable milestones

#### Scenario: Output is not a TTY
- **WHEN** a workflow command runs without `--json` but stdout is not a terminal
- **THEN** the CLI emits line-oriented, non-animated milestones and a final summary without control sequences

### Requirement: Optional interaction
The CLI MAY offer approval or other operator choices interactively when both input and output are terminals. It SHALL provide a flag or environment-independent mode to disable prompts, and SHALL never prompt in JSON or non-interactive execution.

#### Scenario: Interactive approval offered
- **WHEN** a TTY-attached command reaches a manual gate and interaction is enabled
- **THEN** the CLI may offer review, approve, request-changes, reject, and exit choices while clearly showing the default non-destructive action

#### Scenario: Automation reaches a gate
- **WHEN** stdin or stdout is non-interactive or `--no-interactive` is supplied
- **THEN** the command returns the blocked state and semantic actions without waiting for input

### Requirement: Post-mutation confirmation
Lifecycle commands SHALL report the resulting durable workflow state, not merely that a request was accepted.

#### Scenario: Approval succeeds
- **WHEN** an operator approves a manual gate
- **THEN** output confirms the actor and phase, reports checkpoint finalization, identifies the resulting run state, and shows the next eligible action

#### Scenario: Request changes succeeds
- **WHEN** an operator requests changes
- **THEN** output confirms the remediation state, reason, invalidated evidence when applicable, and the command to continue remediation

### Requirement: Actionable error presentation
Human-mode failures SHALL show a concise cause, classified context, durable state impact, and a safe next step. Diagnostic detail and internal identifiers SHALL be available through verbose output without dominating the default message.

#### Scenario: Harness integration unavailable
- **WHEN** a selected harness integration is absent
- **THEN** the CLI identifies the missing integration and prints the exact preview or installation guidance rather than a generic service error

#### Scenario: Run remains resumable after failure
- **WHEN** infrastructure failure leaves a durably resumable run
- **THEN** the CLI identifies the existing change-bound run and recommends `swf run <change>` rather than suggesting a duplicate new run
