# SWF 0.2.0

SWF 0.2.0 adds optional, service-owned intake from an OpenRoad roadmap. An
operator can now ask SWF to select the next eligible roadmap outcome, associate
it with one OpenSpec change and one durable run, and enter the existing SWF
workflow without manually choosing a change name.

This is a pre-1.0 release. The command-line interface, API, stored-state
schema, configuration, and extension contracts may still change. Under the
project's versioning policy, a `0.y.0` release may include breaking changes;
the compatibility boundary for this release is described below.

## What's included

- `swf roadmap new` selects the next eligible OpenRoad item, runs Planning, and
  stops; `swf roadmap run` continues through eligible phases.
- `swf roadmap reconcile` settles a durably recorded, interrupted intake
  without selecting additional work.
- OpenRoad remains authoritative for roadmap validation, priority,
  dependencies, and lifecycle transitions. SWF remains authoritative for run
  execution and never parses the roadmap to reproduce OpenRoad decisions.
- A journaled, per-project intake saga converges after interruption without
  duplicating roadmap links, OpenSpec changes, or SWF runs.
- Roadmap provenance is retained in run state and `run.created` events, with
  stable machine-readable outcomes for selection, resume, recovery, exhaustion,
  invalid roadmaps, and identity conflicts.
- `swf doctor --roadmap` checks the optional OpenRoad dependency and roadmap
  validity without making OpenRoad a prerequisite for direct entry.
- The Pi extension exposes the same roadmap entry operations through the shared
  service API.

## Install and get started

Install the product and matching Pi extension:

```sh
npm install --global @chriskealley/swf@0.2.0
npm install --global @chriskealley/swf-pi@0.2.0
```

For roadmap-driven entry, install OpenRoad 0.2.0 or newer, initialize a valid
roadmap, and verify it before starting work:

```sh
npm install --global @chriskealley/openroad@0.2.0
swf doctor --roadmap
swf roadmap new
```

Direct `swf new <change>` and `swf run <change>` entry remain available and do
not require or inspect OpenRoad.

optional and are required only when selected by a workflow.

## Upgrade, downgrade, and stored state

Upgrading from 0.1.0 introduces stored-state schema version 2. Preview and
apply the migration before using roadmap intake:

```sh
swf migrate --project <project-id>
swf migrate --project <project-id> --apply
```

The migration creates the versioned roadmap-intake journal and preserves
existing run documents and `run-bindings.json`. Existing direct-entry runs load
without fabricated roadmap provenance. Migration rollback restores the backed
up version-1 state.

CLI, service, and Pi-extension compatibility advances to the 0.2 line; upgrade
the product and Pi extension together. Do not force a 0.1 service to write
schema-2 state. Use the supported migration rollback and reinstall 0.1.0 if a
downgrade is required.

## Known limitations

- Roadmap intake reconciles associations for which SWF durably recorded an
  intake intent. OpenRoad 0.2.0 does not expose a machine-readable list of
  externally created links, and SWF will not parse the roadmap to discover
  them; use direct entry with the linked change name.
- OpenRoad is an optional external executable and must be present on `PATH` for
  roadmap commands.
- The product remains pre-1.0 and does not yet carry a stable compatibility
  promise.
- Native Windows service management remains preview-only.
- Homebrew, APT, RPM, container, and curl-based installers are not provided.

## Verify the release

The release candidate is built and verified from protected `main` before
publication. Verification covers formatting, lint, type checking, unit,
integration, and end-to-end tests; reproducible assembly; package contents;
clean-prefix npm installation; CLI and service smoke checks; Pi extension
loading; checksums; and the CycloneDX software bill of materials.

The GitHub release contains the exact product and Pi-extension tarballs
published to npm, together with `checksums.txt`, `sbom.json`, and
`release-evidence.json`. Publication uses workflow-bound npm trusted publishing
and occurs before the Git tag and GitHub release are created.
